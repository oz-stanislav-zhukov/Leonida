### Commands

Write these at the start of a line in a comment here. The tables are updated from them. The tables include every comment up to [this one](https://github.com/ItsNotRexed/Leonida/issues/9522#issuecomment-7114406833). Before you claim, check the comments after it: someone may have claimed the item since.

- `claiming: <ID or new item>` before you start. Check the tables and the open PRs first. A claim counts once posted, unless an earlier claim or open PR covers the item. Agents: read this issue's current body (not a cached copy) and run `gh pr list -R ItsNotRexed/Leonida --state all --search "<ID>"` before claiming; a merged PR means the item is done.
- `status: <ID> <one line>` for progress, and to keep a claim alive (a claim with no draft PR and no `status:` for 12 hours lapses: the item goes back to Up for grabs with a link to your code). A draft PR keeps it too.
- `blocked: <ID> by #N` when you wait on another PR, hardware or the game executable.
- `releasing: <ID>` if you stop; `done: <ID> #PR` when the PR is up.
- `finding: <one line>` for work you found but won't do yourself: a bug, a missing method, a stale doc, a follow-up of your own PR. Below that line: where (file and line), why it matters, and whether it needs game files or particular hardware. The coordinator checks it against existing items and PRs, then adds it to Up for grabs with your name on it.
- In the PR: `Depends on: #N` for every PR yours builds on or conflicts with, and `Fixes #N` for the issue it fixes.

### Decisions for the maintainer

- CI approval for fork PRs.
- Tiled resources (D3D-20): which packed-mip split should the layer follow? AMD RDNA2 and RDNA4 agree with each other; NVIDIA (the layer today) and WARP (never packs) differ. The console is RDNA2. `AC-Storm-YT` will make the change once decided (#374).
- **Ray tracing (D3D-178, `romainveurrier`):** should `BuildRaytracingAccelerationStructure` build the console's XDXR BVH4 records (#1572), which the game's translated RT shaders read, or keep #743's `VkAccelerationStructureKHR`, which they can't read? Proposal: XDXR by default, KHR opt-in. The wiring PR waits on this ([question](https://github.com/ItsNotRexed/Leonida/issues/313#issuecomment-7079038047)).
- **macOS / Apple Silicon (`zneel`, [proposal](https://github.com/ItsNotRexed/Leonida/issues/3381#issuecomment-7085219144)):** best-effort rather than a target that gates the critical path? MoltenVK failures wouldn't block a PR, a macOS CI job would be informational, and Metal workarounds would stay opt-in without changing the default translation. Several open Mac PRs change shared translator code, so the answer affects their review.
- **Overlay location (`kotorvr`, [finding](https://github.com/ItsNotRexed/Leonida/issues/3574#issuecomment-7085828575)):** the default overlay `<game>\overlay` is visible to the title as `GAME:\overlay` (its writes twice, plus the deletion markers). Option 1: hide the overlay root inside `GAME:`. Option 2: move the default out of the game folder (needs a migration note; touches #2957 and #3471). `kotorvr` will implement whichever is chosen.
- **16-bit compare `op_sel` (TEST-644, TEST-650):** `main` honours VOP3 `op_sel` on `v_cmp(x)_*_{f16,u16,i16}`; the only raw-encoding hardware measurement (#3329, gfx1036 via `hw_oracle`) says RDNA2 ignores it and reads the low halves. #3487 followed the hardware and was reverted in round 43 (f99ff6cb), but the probe behind the revert runs the translated path, so it can only agree with the translator (`AirKyzzZ`, #4571). Which rule should the translator follow? A re-measurement needs an RDNA2 GPU. New (`sperm`, #4816): a raw-word hw_oracle run on gfx1036 for every source form (SGPR, inline constant, literal, VGPR) reads the low halves in all of them, a third reproduction of #3329; the constant/literal/SGPR evidence behind the revert came from a probe that runs the translated path. Corpus count (`sperm`, #4933): none of the 154 16-bit VOP3 compares in the 1.0.2.1 corpus (142 programs) sets op_sel, so either rule translates every game shader the same; llvm-mc drops op_sel when disassembling, so only a raw-word fixture can exercise the rule.
- **SHADER-715 sink dword vs the 32 KiB LDS invariant (#3932):** the sink dword makes a 32 KiB-LDS shader 32,772 bytes, which `tests/semantic/test_cs_barrier_counts_lds.py:120-122` forbids. Drop the sink at exactly 32 KiB (fall back to branch checks), or change the test's limit? (`ray3242`, #4683)
- **Repeated merges of the same PR (`paratustra`, #4816):** 193 PR numbers have two or more "Merge pull request #N" commits among the last 2,000 merges, and each repeat of a rebased copy leaves duplicated text on `main` (`docs/models.md` 537-621 = 622-691, `docs/embedded_shaders.md`, README rows). Should the merge step skip a PR whose number already has a merge commit on `main`, or compare its changes with what is there first?
- **Per-fixture expected words (`AwkGrep256`, #4816):** GPU fixtures keep their expected words in shared lists in `scripts/run_gpu_tests.py` (196 open PRs and branches touch it) and `runtime/test/shaders/check.py` (173), so unrelated fixture PRs conflict every merge round. Proposal: a `; expect:` line in each fixture's header, read by both runners, with old fixtures migrating later or never. It needs your OK before anyone codes it.
